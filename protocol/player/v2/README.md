# Player Protocol 2.0 wire baseline

This is the public, cross-language contract. Transport clients must not depend on server authority, private SQLite schemas or checkpoint internals. Client-side prediction may use the public prediction library over authorized observations; the SDK transport remains engine-free. `schema.json` defines exact request structures and response envelopes and extension requests. `fixtures/` contains language-neutral normative cases; `conformance.json` lists active conformance requirements and their implementation checks.

## Transport and identity

Base path `/player/v2`. Requests are strict UTF-8 JSON: reject invalid UTF-8, duplicate keys (including escape-equivalent names), unpaired surrogates, non-finite numbers, non-JSON values, unknown request fields, and nesting deeper than 32. Request bodies are at most 65,536 bytes. Snapshot/event response pages have a separate 262,144-byte budget. Native clients use `Authorization: Bearer <executor grant>` and optionally an opaque `X-Request-Id` for diagnostics. Request IDs are not idempotency keys. Browser requests are same-origin only. Normative wire fixtures contain no usable credentials. Executable fixtures must use temporary synthetic credentials.

Authentication always derives player and scopes from the server's hashed executor-grant record. Claimed player, controller, human, commander or worker headers confer no authority. Executor credentials are distinct from owner credentials. Scope is the exact tuple `serverId`, `roomId`, `roomEpoch`, `playerId`. `playerId` is an opaque, persisted `player-UUID` authorization subject, never a seat number. A verified lobby-to-game compaction carries that subject to its new numeric game seat. Cross-epoch history is readable only through the same verified subject lineage; missing lineage returns unavailable coverage rather than guessing identity from a seat or name. Hello additionally returns the explicit game/lobby/chat mapping. Clients validate the mapping rather than assuming numbering conventions.

`GET /protocol` returns versions, implemented capabilities, limits, ruleset and actual action availability. `POST /sessions/hello` negotiates a supported version and required/optional capabilities, then returns a fresh executor session. Missing required capability fails closed. Discovery separately names `rulesetId`, `rulesetVersion`, `observationSchema` and `commandSchema`. Its compatibility matrix declares current 2.0, previous null and no retirements. Unknown major/minor versions or required capabilities fail closed. Optional response fields are forward-compatible; unknown required events stop writes. The implemented capabilities and their host prerequisites are listed below.

## Numeric and canonical rules

`seq`, `highWatermark`, lease `generation`/command `fence`, `receiptVersion`, `statusSeq`, `instructionsVersion`, and `authorizationVersion` are canonical unsigned decimal STRINGS, at most 78 digits, with no leading zeros except `"0"`. Never decode them as IEEE-754 numbers. Compare arbitrary-precision integers or decimal length then lexicographic digits. Overflow fails closed. `decisionInputVersion` is an opaque UUID baseline, not an ordered counter; compare for equality only. Cursors, sessions, epochs, IDs and page tokens are opaque.

Canonical command intent uses RFC 8785/JCS: sort property names by UTF-16 code units; serialize finite binary64 values with ECMAScript shortest-roundtrip formatting; preserve array order; normalize negative zero to `0`; do not normalize Unicode. SHA-256 hashes the UTF-8 canonical bytes. Intent is `{scope, ...commandWithoutIdempotencyKey}`. The diagnostic request ID and logical key itself are excluded; all immutable command fields, including original session, fence, authorization version, revision, instructions and payload, remain bound. A retry must never substitute a new fence, revision or key.

Engine action IDs are nonempty strings up to 128 UTF-16 code units, preserving existing Unicode identifiers. JSON Schema `maxLength` is a necessary code-point bound; clients must additionally enforce this UTF-16-unit rule where stated. Protocol-generated identifiers use the ASCII schema pattern. Numbers in action payloads mirror existing validators, not new game limits: drillers 1..1e9, recipient 0..9, explicit launch delay 0..86400 (`engine/fleet-scenario.ts:action`). Schedule issueTick is a nonnegative safe integer at the wire boundary; the existing room-relative scheduling validator remains authoritative. No invented fixed-point coordinate conversion or 1e7 schedule cap is applied. Underlying `toggle-funding` and `resign` remain legal capabilities without restoring hidden UI.

## Fixed snapshot pages and exclusive events

`GET /snapshot` creates a bounded bootstrap and returns a `snapshotPage`. A snapshot holds one visible-state cut and event high-watermark H in the same SQLite/room serialization boundary. Continuations use `GET /snapshot?snapshotId=...&pageToken=...`; page tokens are bound to that exact player, epoch, bootstrap and immutable document. Every page repeats identical metadata, H, cursor, opaque decision baseline and SHA-256 snapshotDigest.

The page encoding is `json-text/1`: concatenate `page.text` strings in exact page index order, verify SHA-256 of the resulting UTF-8 text against snapshotDigest, then decode strict JSON once. Fragments never split a Unicode surrogate pair. The complete document is JCS canonical JSON, preserving null, absent fields and unknown markers. Do not decode individual fragments or treat an incomplete document as a usable observation. Validate page count, index, scope and metadata equality. Snapshot documents are at most 8 MiB, two active bootstraps per player, TTL 60 seconds. Completion is `POST /snapshot/{snapshotId}/complete` with `{}`. Expiry or mismatch requires a new bootstrap. Durable event retention currently performs no deletion; pins are explicit for future administrator retention policy.

`GET /events?after=<cursor>&limit=<1..200>&waitMs=<0..1000>` is exclusive-after. `waitMs` defaults to zero; a positive value waits for a scoped event only when the initial page is empty. Waiting releases the room executor and SQLite transaction; the response revalidates authority and reads committed events. Disconnects release the waiter. Each player's immutable filtered stream has its own streamEpoch and decimal seq. A cursor is not a global sequence or numeric offset. A page reports inputCursor, nextCursor, hasMore and coverage `(fromExclusive, toInclusive]`. An empty page returns the input cursor unchanged. Unknown/cross-player/stale cursor is RESYNC_REQUIRED, never a partial-success guess. The stream emits invalidations, not raw omniscient diffs. Clients must discard omitted/redacted data when replacing a snapshot and must not fill unknown values with zero.

## Leases and durable commands

With negotiated capability `actions.batch/1`, `POST /commands/batch` accepts an `order-batch` command containing 1–8 complete `order` commands (`schema.json`). Each child keeps its own immutable command key, client ID, original revision and optional action basis. The parent and children must share epoch, session, fence, authorization version, instruction version and original revision. Nested batches and duplicate keys are rejected before admission. The parent is durably admitted before settlement; settlement first validates every original action basis against one current authorized view, then executes children in order in one serialized SQLite transaction. Each child still checks lease authority, instructions, current legality, resources and manual priority. No external manual command can interleave inside settlement. A rejected child stops the remaining suffix, whose independently queryable receipts use `BATCH_NOT_EXECUTED`; successful prefix effects remain committed. The parent's terminal receipt binds the ordered child receipts. Replaying the same parent returns those receipts without executing again; uncertain delivery is resolved by lookup under the original keys.

The batch response includes the parent's receipt and the first page of one final authorized snapshot. The ordinary snapshot continuation, digest, cursor installation and completion rules apply. The snapshot is a later authorized cut, not necessarily the exact mutation cut. Snapshot delivery failure does not erase committed child receipts or justify resending commands. Servers without the negotiated capability continue to use individual commands.

`GET /control[?sessionId=...]`; `POST /control/acquire`, `/renew`, `/release`. Every operation carries roomEpoch, sessionId and idempotencyKey; renew/release also carry fence; acquire/renew may carry ttlMs (1,000..120,000, default 30,000). Lease expiry is authoritative elapsed time. Wall timestamps are display hints. The response is `{operationResult, current}`. Duplicate operation keys return the original historical operationResult without extending a lease; only current is a newly observed lease state. `current.remainingTtlMs` is the server elapsed-time remainder, never an extension, and clients must conservatively subtract round-trip elapsed time before scheduling work. They must validate current sessionId and generation against the original operation and discard expired/mismatched or delayed old-generation responses. `ttlMs` is the originally configured lifetime, NOT time remaining. Server restart retains epoch and receipts, changes process incarnation, invalidates sessions/leases and increments fences.

`POST /commands` accepts the schema's order, schedule, cancel-schedule, chat-send, chat-seen or readiness envelope. Acceptance is persisted before execution, not a claim of effect. Final settlement rechecks stored grant, epoch, session, fence and deadline; gameplay additionally rechecks the confirmed instruction version. For non-realtime games, the original observation revision remains strict by default. With capability `actions.scoped-revision/1`, immediate launch and return-fleet orders may also carry `actionBasis`, the SHA-256 of the shared `actionBasisMaterial` projection (`action-basis/1`). This scoped digest is checked on first admission and again at settlement; terminal same-key replays return their original receipt. The original `expectedRevision` remains in the persisted request and idempotency digest. Room, player, tick, rules, own resources/units, relevant outposts, incoming fleets, schedules, manual restrictions and agreements are retained; unrelated opponent garrison changes and fleets with known other destinations do not invalidate execution. All own fleets, fleets with unknown destinations, and visible outpost ownership/facility/visibility changes remain conservatively protected. Missing or unsupported action material fails closed. This checks direct execution dependencies, not global strategic equivalence; ordinary authorization, instruction versions, legality and resource checks still apply. The game mutation, final ledger receipt and filtered events commit in one transaction on the same SQLite connection. A callback crossing its lease deadline rolls back. No JSON file or second database is claimed as part of that transaction.

In realtime games (`observation.realtime: true`), immediate `order` commands execute against the current authoritative state: neither an older observation revision nor an older scoped digest alone rejects them, at admission or settlement. The owner command route uses the same rule. Tick changes do not discard an in-flight AI action. Current legality, resources, ownership, visibility, manual command priority, confirmed instructions, grants, leases, fences and durable receipt checks remain enforced. Schedules, cancellations, readiness and non-realtime commands retain their existing version/time constraints. This does not guarantee that an old strategic plan remains beneficial.


`POST /commands/lookup` carries roomEpoch and 1..100 idempotencyKeys. It returns `found`, `absent_within_retained_scope`, or `history_unavailable`, plus explicit authoritative coverage. Missing/unretained epoch is not evidence of nonexecution. Default queryUntil is null and epochs are retained until an administrator implements an explicit retention policy. Transport timeout, dropped response or storage 5xx remains unknown; first reconcile the old logical key. A retained terminal receipt can be returned after takeover without executing again. Accepted records left by a crashed process are terminated as rejected/no effect under the old invalidated lease, not replayed under a new owner.

Errors contain code, category, outcome, safeMessage and requestId. Only a durable terminal rejection establishes no effect for an admitted command. `unknown` must never be rewritten as failed or safe-to-replay. Public failures do not include hidden entity details, private intents, token values, stack traces or provider configuration.

## Diplomacy gameplay

`diplomacy/2` provides formal bilateral agreements in ordinary immediate `order` commands: `propose-agreement` (including counteroffers) and `respond-agreement` (accept/reject/withdraw). Exact action structures are in `schema.json`. A proposal is the proposer's consent; only the recipient may accept or reject that exact version. A counteroffer supersedes it and reverses proposer/recipient roles. Proposal waiting time is 24 ticks; each player may participate in at most 32 open proposals/active agreements, including at most 2 active ceasefires and 2 active joint attacks. Acceptance atomically rechecks both parties' active slots. A full slot produces an acceptance-failed receipt to both parties and leaves the proposal pending. Personal capture fulfilment does not release a slot while the contract remains active; terminal contracts release it.

Ceasefires cover specified participant-owned outposts for exactly 100 ticks from signature. Joint attacks target an active third party for exactly 200 ticks, with each party required to capture any one outpost owned by that enemy. No caller duration/deadline or scheduled signature is allowed. Only an actual enemy outpost capture within the signed window fulfils a party; casualties, defence, fleet battles and pre-signature captures do not count. Each party fulfils independently once, with a fixed +10 trust reward; an unfulfilled party receives a fixed -10 trust penalty at expiry. Ordinary outposts and mines count equally. Trust remains clamped to −100…100, with requested deltas preserved in receipts. A legally processed acceptance can produce an acceptance-failed receipt and leave the proposal pending when current terms or active-agreement limits fail. Command success is not proof of signature.

`observation.diplomacy` exposes only this seat's directed relationships and participating agreements, including all current contracts, eight recent terminal summaries, 64 recent receipts and authorized totals. `GET /diplomacy/receipts?after=0&limit=100` pages the complete authorized receipt collection with referenced contract summaries; optional `through` fixes the exclusive upper cursor. Owner access uses `/owner/diplomacy/receipts`. No hidden battle locations or other players' private agreements are disclosed. Actual signed contracts are authoritative; chat promises do not bind. See the gameplay explanations in `docs/development/diplomacy-agreements.md` and `seat-trust.md`.

## Extensions and authority

All paths below are relative to `/player/v2`. `observe` permits only the authenticated player's filtered observation, visible chat/notifications, and own Commander thread, not another player's state. Other executor scopes are `events.read`, `commands.write`, `control.lease`, `chat.send`, `commander.worker`. These stored scopes, epoch/session and fence are server validated; capabilities do not grant authorization.

- Chat: `GET /chat?after=0&limit=100`, `/chat/search`; `after` is an index in this player's visible collection, not a global chat message ID. `chat-send` payload is `{id,to,text}`, where `to` is null (public), one recipient, or a unique recipient list. `chat-seen` is `{conversation,through}`. Both use the normal durable command envelope.
- Notifications: `GET /notifications?after=0&limit=100`. Indices and cursors remain separate from gameplay event cursors. Snapshot chat/notification collections are bounded tails (last 200), with explicit `fromExclusive` and current `cursor`, not silently complete history.
- Commander: the snapshot contains the complete own thread; `POST /commander/worker` accepts `commanderRequest`. A discussion worker needs a current session and its own scope but no gameplay lease. Notice, reply, proposal and acknowledgement use the SAME durable command ledger and `/commands/lookup`; they cannot confirm directives. Payload version/baseVersion are existing safe-integer Commander document fields; envelope instructionsVersion is a decimal protocol counter.
- Readiness: `POST /commands`, kind `readiness`. Observation-change hints include the authorized world `tick` alongside the revision, so a completed executor can defer same-tick changes without fetching another foreground snapshot. Ready true requires the completed `tick`, which must equal the current authoritative world tick. Later observation, chat or instruction changes within that tick do not reopen it. A different tick or loss of control invalidates completion; unresolved admitted gameplay writes still block it. Readiness never authorizes gameplay under old revisions or instructions. The final advance gate checks tick, control generation and pending writes again.

Human owner operations are a different authenticated role: `/owner/identity`, `/owner/grants` (read/register a caller-supplied token HASH), `/owner/grants/{grantId}/revoke`, `/owner/control`, `/owner/commander`, `/owner/commander/messages`, `/owner/commander/confirm`. They require the server-verified owner identity, not executor tokens or headers. Confirmation binds roomEpoch, proposalId, decimal baseVersion and SHA-256 of JCS `{roomEpoch,playerId,proposalId,baseVersion,text}`; `GET /owner/commander` supplies the digest. No protocol endpoint mints or returns a secret executor token. The owner UI uses owner routes behind the same durable control fence.

## Client calculations and authoritative facts

Forecasts, batch comparisons, route/deployment previews, fleet arrival estimates and attack route/candidate screening execute in the controller or browser using only authorized observations. No remote computation query endpoints or calculation workers are exposed. `activity.read/1` enables paginated `/activity`; actual settlement/history is server-owned, never guessed from disappearing fleets. Browser history remains owner-authorized through `/owner/queries/history`.

## Deadlines, save and restore

Room advancement follows the host clock policy. A finite remote decision profile is explicit only: `PLAYER_REMOTE_DEADLINE_MS` on the laboratory entrypoint, or `remoteDeadlineMs` on the standalone game service (1..86400000). Its fixed authoritative per-turn deadline does not slide with polling, chat, status, offline executors or repeated configuration reads. Ordinary realtime clocks keep their existing policy. During a coordinated checkpoint the world is paused, but the explicit remote deadline is NOT extended; it may already be due after resumption.

Game-only checkpoints store authoritative world, ledger, filtered streams, controls and SQL chat/Commander, not official AI databases, model keys or user-supplied private paths. A supported restore allocates a fresh epoch while still offline, revokes old grants and fences, and only then permits a listener. Ordinary restart retains its epoch but invalidates process-bound sessions/leases. Ended epochs default to retention until an explicit administrator policy is implemented.

The standalone service can optionally advertise `checkpoints.coordinated/1` when its checkpoint publisher is configured. The protocol is prepare → drain → freeze → publish → resume, with finite phase deadlines. `GET /checkpoints/current` and `GET /checkpoints/{checkpointId}` return only this participant's state; `POST /checkpoints/ack` uses the exact `checkpointAcknowledgement` schema. Frozen acknowledgements carry only an opaque receiptId and SHA-256 digest of a private local checkpoint. They do not upload private files, disclose local paths, or claim everyone participated. Durable repeated acknowledgements are idempotent; ambiguous delivery is resolved by reading the same checkpoint/participant before retrying the SAME acknowledgement. Prepare/drain permit existing control renew/release and settlement; freeze/publish/resume reject gameplay/control mutations. A resumed acknowledgement means locally ready to resume, not that a lease has been reacquired. Wait for completed/aborted before acquiring again. Unsupported, missing and timed-out participants are explicit. See `docs/development/coordinated-game-checkpoints.md` and `docs/development/game-only-server.md` for the operator API and private-state boundary.

## Implemented capability and entrypoint matrix

- `core/2`, `actions.order/1`, `actions.schedule/1`, `readiness/1`, `activity.read/1`, `actions.scoped-revision/1`, `manual-commands/1`, `diplomacy/2`: real listener implementations backed by the host's SQLite authority.
- `chat.read/1`, `chat.send/1`, `notifications.read/1`, `commander.read/1`, `commander.worker/1`: advertised by the full domain coordinator only. Legacy JSON is validated and imported once transactionally; original files remain, but are not read as current authority or dual-written.
- `tick-times.read/1`: advertised by hosts that record authoritative tick boundaries. `GET /tick-times?after=0&limit=1000` requires `observe`; `/owner/tick-times` accepts the player owner credential. Pages include server time and elapsed time for the current tick. Boundaries describe actual persistence commits, including waiting/downtime; missing history and multi-tick batches are never interpolated. Clients must not read a workstation database or use workstation wall time to infer durations.
- `checkpoints.coordinated/1`: only the configured standalone checkpoint host. Existing hosted linked checkpoints remain a distinct compatibility path and do not claim remote participation.

The laboratory `main`, lobby/lifecycle entrypoint, and independent game-only service all use the durable v2 owner/executor control. The standalone service has no runtime dependency on AI, SDK, model, UI or legacy linked-checkpoint formats. Run `npm run build` first. `npm run game:start -- --database <existing.sqlite> --access <existing-owner-access.json>` explicitly starts it; `npm run game:checkpoint -- help` describes export/verify/restore. No subcommand means help, never implicit startup. No real access file or credential is created by these examples. Independent standard-library Python/Go clients and the SDK implement writable core and durable event polling. They default to no keepalive, auto-renewal or reconnect. Official runtime private checkpoint participation requires `coordinatedCheckpoints:true` on a v2 seat and is off by default. It independently polls while ordinary model work is paused, drains both gameplay/discussion and unresolved outbox entries, saves only under its existing private store directory, and sends only opaque receiptId/hash. Restarted sessions cannot acknowledge as the selected old participant. Client private-state coverage must never be inferred merely from the server advertising that extension.

### Fixed admission lifetime

`hello.limits.acceptedCommandMs` is 30,000 ms. Each durable `accepted` mutation records its admitting server incarnation and a fixed server-monotonic execution deadline. This is a transport lifetime, not a restriction on legal game actions or scheduled issue ticks. Renewal, lookup, duplicate requests and wall-clock changes never extend it. A lookup, receipt read, control access or readiness gate retires expired accepted work; execution checks the deadline before and after tentative same-transaction computation. Expiry commits `rejected`, `effectCommitted: false`, `code: COMMAND_EXPIRED`, and the next receipt version plus its event atomically. If surfaced as a typed error its category is `replan`, outcome `rejected` (known no effect). Clients must still resolve unknown transport outcomes by authoritative lookup, never infer failure from their own timer. Already committed `scheduled`/`applied` records are never changed to no-effect; schedules still fire. Lease retirement immediately rejects only outstanding fenced admissions; grant revocation also rejects its independent worker admissions. Restart retires old-incarnation admissions. An already-admitted in-flight call may receive its exact stored no-effect terminal after revocation, but revoked credentials cannot authenticate new requests or read ledger endpoints.

## 独立只读投影

`GET /observation` 使用 `observation.read/1` 返回当前授权观察；`GET /commander` 使用 `commander.read/1` 返回本席位指挥官线程。两者均校验 `observe` 授权及响应 scope，不创建或安装分页快照，不消费执行器事件游标，不要求取得游戏控制权。响应结构见 OpenAPI 与 schema，观察和线程内容各自遵循现有可见性及私有数据边界。独立读取可并行，调用方不能假定两个响应属于同一个原子时点。

## Live state synchronization

`state.sync/1` provides `GET /sync` with optional `after`, `waitMs` (0–1000) and authenticated `sessionId`. Control session identity remains masked unless it matches the supplied, grant-scoped session. It returns the current authorized snapshot document, stream cut and control state in one response; matching cursors return a null document. `after` is an equality token, not a replay request: expired history does not prevent installing a fresh full cut. The response is bounded by `snapshotBytes` plus its envelope. It requires both `observe` and `events.read`; scope, visibility and private collection filtering are identical to snapshots. Waiting releases the room executor and SQLite transaction. This endpoint creates no replay pin and requires no completion acknowledgement. Wire fields are defined in schema/OpenAPI.

The official runner continuously installs these complete cuts locally before waking decisions. Normal foreground snapshot reads use the installed cut, without an event check, paginated download or acknowledgement. Synchronization continues during tactical work. Bootstrap, explicit execution guards, accepted-write recovery and missing fact ranges can still require network requests. Local state is the latest successfully synchronized cut, not a guarantee of zero transport lag. Commands retain current server authority, resource, instruction and receipt validation. The SDK's paginated snapshots and event replay remain available for independent clients; live synchronization does not replace durable command reconciliation.
