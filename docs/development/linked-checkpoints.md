# 阶段性联动存档

游戏设置 → 本地存档 → 阶段性联动存档，可输入名称并保存。页面显示等待 AI 收尾、保存中、完成或失败，以及已保存的阶段。存档位于 `LAB_DATA_DIR/checkpoints/<存档编号>/`，默认是 `runtime/checkpoints/`。

保存包含游戏数据库（含指令、事件与现实时间记录）、本局已绑定席位使用的 AI 私有数据库、玩家凭证、聊天及已读位置、司令私聊历史与已确认指示、席位绑定，以及独立控制器的固定槽位配置。其他房间或未绑定席位的 AI 数据库留在运行目录，不进入本局存档。模型 API 密钥沿用控制器现有的仅内存／环境变量策略，不写入存档；恢复后仍需原供应方凭据。网页 JSON 导入／导出仍只处理游戏局面，不是联动存档。

## 保存边界

1. 游戏服务器通过原有串行队列同步当前游戏时间，暂停自动推进和实时时钟，阻止新的人工操作。
2. 经本地交接目录的 `checkpoint-request.json` 通知独立控制器。控制器阻止新轮询、启动和配置变更，等待已开始的观察、模型决策、工具写入、司令私聊刷新／讨论／指示整理及持久回执全部收尾；期间继续维护所需控制租约，已有 AI 命令仍可提交。托管 AI 同样等待观察与决策结束。
3. 控制器释放运输层控制权并冻结数据，使用 SQLite `VACUUM INTO` 保存本局绑定席位对应的私有数据库及固定槽位配置。不会人为中断模型，也不会为了保存新增模型请求或清空记忆。
4. 游戏服务器进入串行写入屏障，保存完整游戏数据库、托管 AI 数据及相关文件。数据库包含已提交 WAL 内容，不直接复制正在写入的 `.sqlite` 主文件。
5. 校验文件 SHA-256、大小、完整文件集合、游戏全量重演及局面／凭证身份后，以目录重命名发布。只有完整成功的目录才出现在已保存列表；`.pending-*` 是未发布的中间数据。
6. 恢复游戏时钟、控制器原控制权及自动推进开关。保存本身不新增 AI 决策；解冻后正常轮询发现新事件时仍可能正常触发决策。AI 已停止、报错等原有事实不会被当作保存操作的授权而强制启动。

协调默认最多等待十分钟。控制器缺失、绑定不一致、复制或校验失败不会发布可用存档，双方执行解冻。保存完成但控制权恢复失败会单独报告警告。进程崩溃时控制器的冻结请求有期限；服务器重启沿用原启动策略，不自动启动 AI。


## 校验与离线恢复

先运行 `npm run build`。校验不重启服务，也不覆盖存档：

```powershell
npm run checkpoint -- verify D:\Projects\Subterfuge\runtime\checkpoints\<存档编号>
npm run checkpoint -- restore D:\Projects\Subterfuge\runtime\checkpoints\<存档编号> D:\Projects\Subterfuge\restored-stage
```

恢复目标必须不存在，其父目录必须存在。工具校验完整存档后，创建新的运行目录；游戏文件置于根目录，AI 文件置于 `independent-agent/`。不会覆盖当前运行目录或自动停止、启动服务。恢复途中失败会保留未完成标记，游戏服务器拒绝启动该目录。

使用恢复局时，先停止原游戏及控制器，等待完整关闭（含在途讨论及回执收尾），保留原运行目录作为退路。不得把仍运行的旧控制器接向恢复后的同一地址；这不是热回滚。设置 `LAB_DATA_DIR` 为恢复目录；控制器的 `--local-game-directory` 指向该目录，`--store-directory` 指向其中的 `independent-agent`。固定槽位配置文件为该目录下的 `controller-slots.json`。控制器需保持原玩家接口地址及端口，因为现有私有数据库按服务器地址、房间及席位共同隔离；更换地址会使用另一份私有记录。

恢复保留房间、凭证、聊天、原有命令及 AI 历史，自动推进关闭，AI 按现有启动规则暂停。实时对局首次启动时将现实时间锚点平移至存档阶段，避免把保存后的现实时间全部补算进去；之后仍按既有实时时钟运行。恢复后的新 AI 决策可能产生不同走向。

本功能沿用当前存档格式的严格校验，不新增旧开发存档的自动迁移。规则变更导致旧存档失效时，按项目开发期存档约定处理。

## 协调重启

Windows 手动／测试自动推进局可在项目根目录使用快速入口。它发现实际监督进程、数据目录与绑定，先校验或统一构建，再执行以下协调流程；普通重启保留原局和各席位运行意图。新局只能通过显式 `--new-game` 创建。

```powershell
# 只读检查与执行计划，不构建、不暂停、不调用模型
node scripts/quick-restart.mjs --dry-run
# 保留当前对局，联动重启两边
node scripts/quick-restart.mjs
# 明确新建测试局，沿用前六个槽位现有模型与策略（可混合供应商）
node scripts/quick-restart.mjs --new-game --bots 6 --provider existing
# 更新后重启，并新建六个 MiniMax bot 的测试局
node scripts/quick-restart.mjs --update --new-game --bots 6 --provider minimax
```

`--update` 执行 fetch 与上游快进合并，不重置或暂存已有修改。新测试默认种子 4300，可用 `--seed` 指定；仅新测试接受 `--bots`、`--provider` 和 `--seed`。`--provider existing` 保留所选槽位的模型与策略，不切换供应商；槽位须已有模型配置，实际完成验证仍必需。实际端口不同可指定 `--game-port`、`--player-port`、`--console-port`，默认分别为 4310、4311、4400。入口要求两边已有开发监督进程；实时局使用下方协调流程，不能通过切换时钟规避检查。

构建只运行一次 `web:build`，包括边界检查、TypeScript 和两边前端。`runtime/.dev-build-receipt.json` 记录源码、构建产物、Node 版本与项目位置的指纹；全部一致才复用。两边监督进程收到 `SUBTERFUGE_PREBUILT_RECEIPT` 后分别重新校验，不能把过期产物当成当前构建。普通 `web:dev`、`ai:dev` 仍按原方式构建，监听行为保持。构建时源码变化、进程或运行意图变化会中止后续重启。

快速入口保留联动存档、在途工作收尾、实际凭据身份校验和精确进程核对，既不热拷贝数据库，也不清理数据库或 WAL。需要恢复的环境密钥必须在启动环境可用；仅在控制台内存设置的密钥会阻止冷重启。新 MiniMax 测试要求 `MINIMAX_API_KEY`，沿用槽位策略，必要时选择 MiniMax 预设。显式新局前仍先核对原局恢复结果。

各阶段自动轮询就绪，不用固定长等待；同步导出大库期间的存档状态 GET 超时会在同一任务的总时限内继续检查，不重发保存或其他写入请求；席位启动须 job 完成且持有控制权。新测试还须每个模型出现本次启动后的正常返回和 token 用量；普通自动推进局先恢复推进，再观察自然触发的模型返回。模型返回与结果发布分别计数：正常返回后过时或依据失效仍证明调用完成，校验拒绝、供应商失败及未完成调用不能作为成功证据。原本不推进的局只验收启动与控制权，不强制新增一轮；原先暂停的席位不为验收额外启动。自动推进须实际增长 tick。阶段耗时、结果和两边日志写入 `outputs/quick-restart/<运行编号>/`；出错保留证据和数据库，不自动重建或重发操作。`runtime/.quick-restart.lock` 防止并发执行；若执行进程崩溃，先确认记录 PID 已退出再精确移除该文件。

1. 记录真实监督/子进程、端口、房间、tick、绑定、启用意图、完整设置与凭据摘要。
2. 关闭自动推进，保存联动快照并确认完成；暂停授权席位，等在途决策、讨论、回执收尾和租约释放。
3. 记录暂停世界及配置基线，再停止已核实属于本项目的游戏和控制器监督/子进程，核对端口释放。
4. 构建后先启动游戏，核对同局与暂停世界，再启动控制器，核对绑定、凭据、模型及策略；仅处理确认原进程已退出的精确失效锁。
5. 恢复原先明确启用的席位和推进意图，观察真实模型/程序计算完成、有效租约及自然推进。不要重发未知命令或重启正常终局。

Windows 强制信号不保证 finally 执行；须先通过控制接口收尾，不能仅凭进程退出推断数据库和租约已妥善关闭。本机回环加入 NO_PROXY，同时保留外部模型代理。
