# 大厅与房间生命周期

## 启动与身份

```powershell
npm run lobby:start
```

默认 http://127.0.0.1:4312 ，多房间目录为 `runtime-rooms`。`LOBBY_PORT`、`LOBBY_HOST`、`LOBBY_DATA_DIR` 可配置。实验室数据独立，不被大厅创建覆盖。

房间容量 2–10 人。网页玩家从大厅房间列表点击“加入”直接进入等待室，不输入加入码；创建者设置名称、人数与时间模式后直接进入房主席位。已有身份显示“进入”，可以返回满员或已开局的房间。返回时优先用该房间保存的玩家凭据向服务器核验席位，不依赖领取记录，也不重新占位；只有领取记录时沿用原领取键恢复身份。网页不显示房间码及复制邀请入口。

底层仍以六位大写字母数字房间码标识房间，供 AI、公开接口及运维使用；通过 `subterfuge rooms` 可查询。领取返回本人凭据，公开房间标识不是已占席位的控制凭据。同领取键重试恢复相同身份，不能冒领其他人。进入正式阶段后不接受新的领取键。

## 时间模式

创建时使用[房间时间设置](../../packages/contracts/src/room-timing.ts)：实时模式设置每 tick 的现实秒数，允许 1–3600 秒整数，默认 10 秒；回合模式不接受 tick 时长。模式创建后不可更换，同一创建键不能改用另一套时间设置。房间列表和等待室显示模式与实时 tick 时长。

两种模式都保留开局前现实 5 分钟集结倒计时。实时模式按持久化的房间时钟推进和离线补算；回合模式不补算墙钟时间，所有存活席位确认当前 tick 就绪后才推进一次。真人使用玩家页“本回合就绪／取消就绪”，AI 使用既有执行器就绪协议；未就绪、暂停或掉线的存活席位不会被跳过，已淘汰席位不阻塞。

真人就绪保存到该房间数据库，重启后保留；AI 必须持有有效控制与当前就绪声明，重启清除的租约不能算作就绪。旧 tick 的报告拒绝，游戏指令会取消该玩家的真人就绪，普通签到不会取消。每次推进清空旧回合就绪；程序为已确认就绪的存活席位记录签到，再结算下一 tick。操作权限与开局席位压缩映射保持不变。

## 恢复与终局保留

大厅先监听 HTTP，再逐房间在独立工作线程中恢复；恢复中的房间显示“正在恢复”，单个房间失败显示“恢复失败”，不阻止其他房间或创建入口。恢复期间原领取键重试返回暂时不可用，不创建重复房间。失败房间保留数据供排查，不能自动清理为终局。

宿主使用私有 SQLite 恢复检查点，保存已验证状态和派生事件日志，每 60 tick 更新，等待、开局、终局及正常关闭时按需要保存。检查点绑定权威源码构建指纹及原记录摘要；同构建恢复检查点后，只重演后续指令与结算。检查点损坏、版本变化或来源不一致时，在工作线程中执行完整恢复，不放宽快照校验。复用检查点的房间恢复后，另外执行后台完整重放审计；审计失败只隔离该房间。检查点不是玩家可导入的存档或身份来源。

已结束对局停止时钟及运行时间写入，单独列在默认收起的“已结束对局”中。按服务端时钟与权威终局事件确定实际结束时间，保留最新 5 局；结束时间相同则按创建时间、房间标识排序。已保留终局允许原玩家返回查看，不接受新席位。

恢复完成和后续终局提交会触发清理，另有每分钟重试。只删除排在前 5 局以外、通过恢复审计且仍为终局的房间：停止该房间服务、排空请求、关闭数据库，核对真实路径后，将房间目录改名为待清理目录并移除，包含数据库、WAL、聊天、控制记录及房间元数据。中途退出留下的待清理目录会在下次启动继续清理。未结束、取消及恢复失败的房间不参与此规则；独立备份按运维备份策略管理。

## 流程

1. 创建房间，或从大厅房间列表直接加入。
2. 等待室显示成员及本人授权海域，尚未加入者只读大厅元数据。
3. 至少两人加入后，房主提交开始，统一倒计时现实 5 分钟；提前开局可按实际参与者压缩游戏席位。
4. 开始倒计时按现实时间运行，倒计时阶段逻辑 tick 与步内时间冻结。
5. 正式开始后使用同一凭据，按权威 game/lobby/chat 映射读取游戏。

服务器在 tick 提交事务中保存计时边界，通过玩家协议的 `tick-times.read/1` 能力提供只读分页；等待倒计时不计为游戏 tick。升级前未记录的区间不补造，每个房间的计时与身份隔离，详见[本机控制台](ai-runtime.md#本机控制台)。

gameSeat 可随开局压缩变化，聊天身份仍是原加入身份。历史私聊、已读和凭据不会按压缩后的同号席位转给别人。客户端在阶段或身份变化时撤下旧观察，再加载新投影。

退出等待室在同一事务召回相关舰队并返还单位；内部召回不是普通玩家命令。提前开始涉及地图重建及预约处理时须显示操作后果，不能静默清除。

等待室统一提供“离开房间”：普通玩家确认后退出席位，房主确认后取消房间并让所有玩家退出，成功后返回大厅。确认失败时保留当前身份与错误提示。开局倒计时及正式对局仅提供“返回大厅”，不退出游戏席位或触发投降。

## HTTP

多房间宿主的 `/api/rooms` 创建、`/api/rooms/:code/join` 领取由宿主校验。领取可指定等待中的确切空席位；同领取键不得改绑其他席位，竞争失败不自动换位。房间授权生命周期接口为：

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | /lobby/v2 | 当前成员、revision、阶段与本人映射 |
| POST | /lobby/v2/commands | join、leave、cancel、start |
| GET / POST | /lobby/v2/turn | 当前回合就绪列表／本人就绪；仅回合局正式阶段，body 为当前 tick 与 ready，不能指定其他席位 |
| GET | /lobby/v2/events | 本身份生命周期事件分页 |

大厅宿主另提供 `GET /api/rooms/:code/identity`，以 owner 凭据确认该房间中的本人已占席位；不会根据客户端指定席位或列表消失推断身份。`GET /api/rooms/:code/bots` 返回公开连接标记；`POST` 续报与 `DELETE` 断开只允许修改凭据所属的已加入席位。房间列表的结构来源为[房间列表 wire 类型](../../packages/contracts/src/hub-room.ts)，恢复中或失败时人数与容量为 0，界面不展示占位人数。席位连接结构来源为[宿主连接 wire 类型](../../packages/contracts/src/hub-bot-link.ts)。连接记录持久保存在房间 SQLite，30 秒未续报即失效；相同连接可续报，不同连接不能覆盖未过期记录。浏览器授权及本机控制台操作见[运行说明](ai-runtime.md#本机控制台)。

命令包含稳定 ID 与当前 revision，身份来自凭据，不能指定他人玩家或自带世界。相同 ID 同操作保持幂等；开局重试不重置倒计时。世界、成员、领取身份与事件按宿主事务边界提交。生命周期游标不是游戏事件游标。

## bot 与运行边界

房间席位提供“绑定 bot”：已占席位仅本人可绑定，等待阶段空位在控制器确认时精确领取；选择未绑定固定槽位，可同步设置模型，成功后保持暂停。等待室（waiting）不请求模型；进入倒计时后刷新权威映射并协商执行器会话，可以进行授权规划与预约，真实世界仍在倒计时结束后才推进。已有绑定不能被新领取静默替换。配置式运行器继续按显式身份连接。

服务端持续处理时钟，关闭页面不暂停。每房间独立状态；已结束对局按本页保留策略自动清理，未结束对局不会因此删除。默认监听回环；公开部署使用明确网络配置和 HTTPS，控制器不能把多房间身份当同一 roomId。

实现入口：`packages/server/src/room-hub-main.ts`、`room-hub.ts`、`lifecycle-service.ts`、`lobby-api.ts`。
