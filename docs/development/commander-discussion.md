# 指挥官讨论与确认指令

这是玩家与己方分层协同 bot 的私有作战讨论，不属于外交或管理员控制。配置模型后可讨论并确认自然语言要求；未配置模型时不解析新要求，前台保留当前约束并报告就绪。

## 交互

底部输入可引用当前合法可见的据点和舰队；插入引用不自动发送。回复优先使用简短自然语言，按授权名单显示玩家名字和完整据点名。历史引用不能泄露失去视野后的实时位置。

讨论只返回答复和待确认提案，不执行游戏工具。提案须明确展示合并后的要求及变动，玩家单独确认后才生效。确认绑定房间、玩家、原版本、提案与正文摘要，过时提案不能覆盖更新指令。

提案正文直接写确认后执行的完整要求，不包含模板标题或“玩家确认后”等界面流程条件。提案合并当前已确认正文与玩家本次明确变更，不因“保持现状”自动把自主战略、笔记或执行参数转成新增指令；已确认正文为空时没有需要保留的旧指令。仅讨论而未要求变更时不生成提案。撤销全部指令使用正文为空的待确认提案，不将清空动作或保留历史改写成新指令。真正的敌情、资源与安全条件保留。hybrid 讨论提供当前授权观察生成的可调兵量估算、进攻候选、来源与航程，以及相关对手据点事实；这些是初筛建议，仍须由执行层验证，不要求玩家手工补齐程序已能计算的参数。

## 指令与执行

唯一有效要求是当前已确认的指挥官指令。战略、笔记和计划是执行安排，不是第二套指令。玩家确认后只显示一次“指挥官指令已保存，AI 将调整原有策略。”后台战略整理完成只更新内部回执与已处理版本，不追加第二条成功反馈；具体游戏行动以任务状态及实际提交、结算记录为准。

“收到”不代表“执行”。已经接受的命令、预约和舰队不会因文字改变自动撤销。已实际完成的原文条款可通过正常决策的事实依据清理；未完成目标、持续约束和仅在途结果保留。

hybrid 的内部指挥官整理回执只证明战略文字已整理；后台执行意图的发布与具体行动分别看分层协同任务及实际回执。整理失败时仍保留错误通知及已确认指令，明确告知尚未完成新的执行安排，不把保存状态当作已经出兵。

指定来源到指定友方地点的调兵通过分层协同的运输任务执行，不能用“来源清空”和“目的地补足”替代该运输关系。单线与先集结后进攻采用明确的范围任务，具体参数和执行限制见[分层协同意图](hybrid-bot-guide.md)。在途运输承诺跨轮保留，离港不算交付完成；普通收益搜索不能自行撤回指挥官调动。已确认正文保留，但当前安排缺少已识别的路线或阶段表达时，保持现状并交后台重新整理，不要求玩家重新确认同一正文。

## 并发与协议

讨论与整理使用独立 Commander 输出协议，不接受普通游戏工具。指挥官线程轮询只读取当前席位的私有线程；讨论所需观察通过独立只读接口获取，不安装前台快照、不推进其事件游标，也不占用前台读取和就绪状态。讨论、模型及回执等待均不阻塞程序前台；仅玩家确认后的指令作为版本化约束进入后续合法决策。讨论 worker 使用自己的授权 scope 和版本核验，不能确认玩家提案。普通决策不因讨论获得额外权限；两者共享模型队列，讨论有预留容量。

讨论在获得模型队列名额后、实际发送前读取最新授权局势，并重新构造整份讨论材料；实时与回合对局均不因排队期间的局势或 tick 变化取消本次发送。身份、已确认指令、消息状态和私有策略版本仍须核验，变化时重新整理，不将旧战略绑定到新的资料依据。讨论回复与提案不直接执行游戏行动，实际行动仍按提交时的规则校验。

服务端通过 owner 路由处理玩家消息和确认，执行器 worker 使用正常持久命令账本及批量查账。连接缺失时保留等待，不自动配置模型或启动席位。暂停与 checkpoint 需等待已开始的讨论、整理和回执收尾。

记录与用量属于私有数据，按房间和玩家隔离；完成调用用供应方实际 Token，失败或缺失用量标未知。实现入口为 `controller/runtime/commander-worker.ts` 和 `controller/contracts/commander-protocol.ts`。

后台战略与指令转译先核对发送时的权限，再核对发布时的当前权限。回复符合发送时权限，但等待期间任务到期、归属或其他权限发生变化时，旧结果不发布，由调度根据最新事实重新整理；指挥官分段结果整体失效时重新整理全部分段。该过程保留原调用审计，不追加格式修复提示词，也不重发已接受的游戏命令。违反发送时权限的结果仍直接拒绝，不自动重试。

模型返回格式不合法或内容未通过协议校验时，丢弃本次结果并保留失败原因，不追加格式纠正提示词，也不自动再次调用模型。JSON 语法诊断只保留输出结构标记和解析器可提供的出错字符偏移，不保存回复正文；偏移对应解析器实际处理的 JSON 内容。已确认指令继续保存，未通过校验的安排不生效。新消息只发起本条讨论，不解除旧指令版本的整理失败暂停；待处理讨论优先于尚未开始的指令整理，讨论完成后再独立处理未失败的新确认版本。新的确认指令版本可发起新的整理。结果未知的调用继续按现有审计与回执恢复机制处理，不盲目重发；已经提交的战略整理只重试通知与确认回执。
